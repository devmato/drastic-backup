# User Guide

dRastic Backup separates the web server from the machines that actually read files and execute backups.

## Concepts

- **Server** -- Hosts the web UI, API, database connection, and integrated restic REST endpoint.
- **Agent** -- Runs on a machine that should be backed up or should execute backup tasks.
- **Repository** -- A restic target. It can be managed by dRastic or configured manually as a custom repository.
- **Job** -- Defines what an agent backs up.
- **Schedule** -- Runs a job automatically with a selected repository and optional repository check.
- **Backup chain** -- Runs existing jobs in order, potentially on different agents.
- **Retention** -- Keeps whole backup runs according to a job policy, including partial/failed runs with snapshots. The newest confirmed complete run remains protected.

## Normal Workflow

1. Deploy the server stack.
2. Sign in with the configured bootstrap admin account.
3. Create or verify a repository.
4. Install an agent and register it against the server.
5. Assign repositories to the agent.
6. Create a backup job.
7. Add a schedule or run the job manually.
8. Restore sample files to a separate empty directory and compare their contents.
9. Monitor reports and repeat restore checks regularly.

## Agent Display Names

Open an agent under **Agents** and set **Display name (optional)** on the **Info** tab. Save it to use this alias in lists, agent selections, reports, and recovery exports. This also works while the agent is offline.

Clear the field and save to use the hostname again. Names are limited to 255 characters; surrounding whitespace is removed. If no hostname is available, the agent ID is shown instead. The technical hostname remains visible in the agent properties, and reconnecting does not overwrite the alias.

## Repositories

dRastic supports two repository types:

- **Native repositories** are created and stored by the integrated `rest-server` service.
- **Custom repositories** use an existing or new restic target, with a location, password, and optional environment variables.

Native repositories are the simplest option for a single dRastic deployment. Custom repositories are useful when you already operate restic storage separately.

Repository passwords can be generated by dRastic or set manually during repository creation. Revealing a repository password requires the account password, and assigning repository access to an agent may ask for password confirmation if the browser no longer has the recovery key in memory. Changing repository passwords after creation is not supported yet.

## Time Zone

The first successful browser login initializes the account's unset time zone from the browser. Later logins keep the stored choice, including an explicit UTC setting, even when the browser's zone changes. Without a usable browser zone, login still works and schedules use UTC until a later login or manual save initializes the setting.

Open **User menu > Settings > Preferences**, search for a zone in **Zeitzone** (for example `Europe/Berlin`) and click **Save** to choose it manually. All your job and backup-chain calendar schedules use this zone. Offline agents receive changes on their next successful synchronization. Periodic intervals remain UTC-based; report timestamps remain absolute instants. Changing the zone changes future calendar execution times. See [Backup and Restore](backup-and-restore.md#create-a-schedule) for upgrade and daylight-saving behavior.

API clients may include an optional IANA `schedule_timezone` in `POST /api/auth/login`. Only a valid zone on a successfully authenticated, still-unset account is stored; omitted or unsupported browser zones do not prevent login. Concurrent initialization cannot overwrite an already saved choice. `GET /api/user/` returns `schedule_timezone: null` while unset; agent synchronization, previews, chains and Recovery Export use the effective UTC fallback.

## Account Password

Open **User menu > Settings > Account & Recovery > Change Password** to change the signed-in account password. The dialog requires the current password and a new password.

Changing the account password re-encrypts the account recovery key for the new password and revokes existing sessions and debug access, so sign in again after the change completes. Settings also contains Recovery Export and [opt-in Debug MCP](debug-access.md), with one diagnostic switch for all your agents. The browser's light/dark preference remains directly accessible in the user menu.

## Jobs

| Type | Source | Requirements |
| --- | --- | --- |
| File | Live files and folders | Read access on the agent host |
| Proxmox | QEMU VM disks and configuration | Root agent on the Proxmox node; mode-specific host tools |
| TrueNAS | Files from temporary ZFS snapshots | Agent app on the NAS, API permissions and verified snapshot mounts |

All job types use an available/selected split view, stacked on smaller screens. **Advanced** below the selection opens custom file exclude patterns, TrueNAS exclude patterns, or the optional Proxmox temporary storage override. Settings remain part of the job when Advanced is collapsed.

Proxmox offers **Snapshot**, **Native — read all disks**, and **Native — with CBT**. CBT reuses unchanged blocks only with a confirmed checkpoint; otherwise it performs a full native read. Each backup is independently restorable. Legacy VMA archives remain recoverable as files, not through the specialized VM restore modes. See [Backup and Restore](backup-and-restore.md) for prerequisites and limitations.

Only create jobs for data the agent can actually access. Docker agents typically mount the host filesystem read-only under `/mnt/host`.

Run repository checks manually when validating storage, or enable a post-backup repository check on schedules when the extra runtime is acceptable.

## Notifications

Notifications are queued after an operation report has been committed, so a provider failure does not change the operation result. Each matching operation state and notification configuration creates at most one persistent delivery. Failed deliveries remain pending and are retried when later agent operation reports are processed; there is no independent timed retry worker, so delivery is not guaranteed while no further reports arrive.
